# 10点场：行动顺序与鬼火对照（2026-10-12）

## 结论与核验范围

**当前模拟与实机不完全一致。本轮及胜率追查共修复五项有证据的问题，开局前四个正常回合及天井下首次回合供火已对齐，整局尚未对齐。用户指出红方100%后，继续发现并修正荒骷髅攻击击杀后无限复活的问题；种子1现在已从红胜变成蓝胜。**

### 胜率截图后的补充：荒骷髅被错误实现成不死单位

旧 `unit-defeated` 分支只判断目标是荒骷髅且被动有效，就以1生命复活；没有判断死亡来自生命流失还是攻击伤害。客户端5852保护的是“失去生命”，不能扩展成普通攻击、技能或真实攻击均无法击杀。

修复前种子1的完整事件中，荒骷髅被犬夜叉等攻击击杀后复活了22次。这比早期行动条误差更直接地改变整局胜负，也说明只检查开局数字是不够的。

现在死亡事件明确携带 `damage` / `life-loss` 原因，生命流失保护只对后一种生效。普通及真实攻击击杀不再触发该复活。新增两项回归：普通/真实攻击致死不复活，以及本场完整种子1战斗不复活且蓝胜。生命流失保命的原有测试仍通过。

对照实验采用基础种子1派生的同一组10个样本，仅在诊断注册表恢复旧死亡保护条件，其他实现均保持当前版本：

| 规则 | 蓝胜 | 红胜 | 攻击击杀后的荒骷髅复活 |
| --- | --- | --- | --- |
| 旧死亡保护条件 | 0/10 | 10/10 | 7个样本出现错误复活 |
| 修正死亡原因判定 | 7/10 | 3/10 | 全部消失 |

该实验说明错误复活足以使同一组样本从红方100%改变为红方30%，并不证明实机真实胜率就是蓝方70%。用户截图的随机种子未知，不声称实验重放了截图中的十个具体样本。UI已有模拟记录不会自动改写，应重新执行模拟。

实机输入为 `C:\Users\Administrator\Documents\MuMu共享文件夹\VideoRecords\10点场` 的 5,498 张连续 JPG。按帧序抽查全程行动展示和蓝方鬼火，关键差异再查相邻原图；不是逐张识别所有伤害和状态。帧号不是时间戳，不假设录像帧率。

阵容按用户本次截图复录，保存在 `desktop/tests/fixtures/duel-10am-lineup.json`。技能等级截图未显示，本轮按界面默认全部五级；没有客户端随机种子和原生单位 UID。复现种子为 1、上限 600 次行动。其他种子的早期扫描同样没有消除天井下之后的第一处分叉，不能把这处分叉全部归于随机数。

红方：慧明灯212/钓瓶火、荒骷髅208/薙魂、追月神181/薙魂、御馔津137/破势、不知火135/蚌精。

这里必须区分三类信息：

- **正常回合**：用行动圈、技能和前后帧判断；模拟对应 `turn-started`。
- **额外回合、反击、被动、邀战**：可能换头像或弹出技能横幅，不能每次都计为普通行动，尤其是慧明灯反应、御馔津封魔箭和荒骷髅时之隙。
- **鬼火显示**：底部可读的是蓝方；回火动画中间值不当作稳定结算值。红方鬼火无法直接从本录像验证，报告不把模拟红方数值当实机读数。

## 行动与鬼火核验阶段修复的四项

### 1. 迅风开局20点被误算成20%拉条

旧实现初始化行动值20时同时加20行动条，使初翎山风赶在天井下前行动。客户端3572说明分别写“战斗开始后”获得点数拉条，以及五级“战斗开始时”获得20行动值。初始化点数不等于战斗中的一次获点事件。

现在只初始化行动值20，不推进初翎行动条；战斗开始后实际获得点数仍照常拉条。整套截图阵容回归检查了前四位，而不只检查单个状态数值。

### 2. 天井下自身错误消耗欢愉、供火和拉条

客户端3233状态写明“其他友方回合结束”消耗一层并获得1火。000500–000600首次再会之音结束仍为4火，不能解释为自身也获得1火。

现在自身回合结束不消费欢愉、不供1火、不拉自身25%行动条。其他非召唤友方回合结束才消费。3233技能同时说明有欢愉时保持清醒；现在清醒增益持续至最后一层被消费，而不是刚施放完就在自身回合末消失。

### 3. 普通回合鬼火条推进阶段不符客户端

旧实现只在回合结束推进普通鬼火条。客户端 `TurnMgrComp.enterLockState` 推进 `addGuihuoBout`，`leaveLockState` 处理满条补火；现在拆成入场推进、离场结算。满条待结算不提前增加可用鬼火，因此这一回合选招不能花尚未到账的火。

钓瓶火、追月神等主动推进仍使用原来的立即结算路径。若已有满条等待结算又遇到额外推进，先支付旧满条并保留新的进度，避免丢失推进。保留鬼火上限8及供火量3、4、5的递增规则。

这是阶段修复，**不代表整局所有补火节点已吻合**。实机大约001350、002475、003450、004350、005225能看到供火/上限变化，后文列出稳定值。004325处有供火动画，不用其中瞬间2火反推完整选招前资源。

### 4. 真实伤害被普通状态增伤再次放大

实机000401/000421附近黄泉战旗：自损20,452，两段伤害1,636、6,135。模拟本轮修复前：自损同样20,452，却打约2,062、7,731。

额外26%来自御馔津四层符咒8%与不知火当时星火18%。这不是技能倍率或生命乘区的问题，而是通用结算又把普通状态增伤乘到了真实伤害上。

客户端 `com/utils/formula.py` 的 `directDamageCalc` 使用传入的伤害，不经过 `calcRawAttackDmg` 的普通伤害增减属性。现在真实伤害跳过通用 `damage` / `damageTaken` 状态乘区，仍保留显式内容回调、分担、护盾及命中事件。

新整阵容回归的截断数值为 **20,452 / 1,636 / 6,135**，三项均与帧相同。此前单独测试荒骷髅时没有带御馔津和不知火增伤，没能发现这项组合错误。

## 仍未对齐的原因

### A. 天井下之后，御馔津仍抢在初翎之前

种子1在天井下结束后确实触发了御馔津封魔箭，并使迅风获10点、初翎拉10行动条；不是没有触发这次拉条。

当前事件：初翎行动条83.9779→93.9779。随后自然推进到御馔津满条时，初翎为99.5033，差约 **0.497个百分点**，所以模拟锁定御馔津。实机000650已经是初翎的岚。

目前只能确定参与排序的状态/速度或事件时序仍有差异，尚未确定具体是哪项。截图速度是整数，真实内部精度未知；各增速效果的精确生效、失效节点也需要继续核对。原生排序包含 UID，但当前两者未同时满条，单纯改同速排序无法解释这个差值。

客户端 `_updateTurnPosOnce` 也有按领跑者剩余距离和速度比例推进的逻辑，不能仅因录像按帧播放就认定是“固定帧取整”造成。未加0.5%补偿或硬编码这局顺序。

### B. 攻击目标不同，使血线、AI、后续鬼火连锁改变

实机000900荒骷髅额外黄泉战旗打到萤草，001025不知火初舞打到初翎。种子1模拟的荒骷髅额外回合及不知火普攻均持续选择天井下。当前部分选敌逻辑优先最低生命比例，容易连续集火同一个目标；荒骷髅正常黄泉战旗则按最高当前生命选择，额外回合使用了另一路目标选择。

这是一项明确的行为差异，但单局选中萤草不能证明额外回合永远选萤草，也不能据此证明官方随机选敌或某个固定优先规则。官方这一分支的完整AI仍需证据；本轮没有按录像硬写选敌目标。

化鲸第一次行动前：

- 修复真实伤害前，模拟天井下约12.9%生命。
- 修复后约23.5%，其他四名蓝方约100%。
- 当前化鲸AI在有友方生命低于40%且有足够火时选付费治疗；因此仍选体甲，3−2+欢愉1=2。
- 实机001250横幅明确为普攻“吸取”，3火未支付技能费用，随后欢愉供1火到4。实机天井下血条也明显高于模拟，但不按截图像素声称精确百分比。

所以本处不应直接改体甲的2火费用或强制化鲸普攻；需要先校准此前选敌与血线，另核实化鲸官方AI分支。真实伤害修正已经缓解血线偏差，但尚不足以跨过40%选招门槛。

### C. 回火累计已受行动顺序、控制和选招影响

实机第一段蓝方展示为：天井下 → 初翎 → 犬夜叉 → 化鲸 → 萤草 → 初翎。当前模拟蓝方正常回合为：天井下 → 初翎 → 犬夜叉 → 化鲸 → 初翎 → 萤草。到这里不只是鬼火余额不同，推进回火条的行动者也已经不同。

后续封印、沉默、欢愉、体甲拉条和迅风获点会进一步改变顺序及资源。初翎和御馔津有概率事件；录像与种子1不共享随机数，具体暴击/射箭结果不能要求逐项相同。不过已经观测到的确定性开局差异和目标策略差异不能用随机性掩盖。

实机结果为蓝方胜；行动与鬼火四项修复之后、死亡原因修复之前，种子1仍为红方胜；死亡原因修复后种子1已为蓝方胜。但前面描述的行动与选敌分叉仍存在，不能因赢家相同就宣称整局复现成功，也不能据这一局给出阵容胜率。

## 复现与验证

在 `desktop` 目录运行：

```powershell
npm run build:renderer-tests
node scripts/duel-frame-10am-repro.cjs 1
node scripts/duel-frame-10am-winrate-repro.cjs 10 1
```

- `sim-1.json`：完整战斗事件，含伤害、控制、行动条和资源来源。
- `turns-1.json`：按回合整理的行动、选敌、入场/离场两方鬼火及进度条。
- 标准输出：顺序摘要。回合中的反击以独立调度类型列出，不能计入普通回合；部分预结算被动攻击没有 `action-declared`，应查完整事件。

回归：`npm run test:duel`，**714通过、0失败**；`npm run typecheck` 通过；`git diff --check` 无空白错误。
