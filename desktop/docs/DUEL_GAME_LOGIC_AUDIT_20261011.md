## 确认未完善的机制

### A. 优先修复：状态生命周期没有完整接入

**A1：施法者回合和整轮状态缺通用自动到期。**

`status-lifecycle.ts` 虽然支持 `source-turn`、`round`、`event`，但正常回合和调度新回合的 `run-battle.ts:164,240` 都只捕获 `target-turn`。轮数在 `:386` 增加时没有推进 `round` 状态，也没有施法者回合通用推进调用。

本次用两单位、无伤害动作做了实际运行复现：三个状态均剩 1 回合；跑到 6 次行动、轮数 4 后，目标回合状态被移除，施法者回合与整轮状态仍为 1。

影响：若内容模块没有另写移除逻辑，这些状态会一直保留。注册表中有 44 个 `source-turn` 和 7 个 `round` 定义；这是潜在影响面，不能直接断言 51 个都错。实际例子包括兵俑石甲、部分结界，以及缚骨清姬的“本轮已召唤”标记。

证据：[运行复现结果](../out/duel-audit-20261011-lifecycle-repro.json)、`content/bingyong.ts:64`、`content/bone-bound-princess.ts:89`。

**A2：阵亡没有统一按 keepOnDie 清状态。**

游戏 `force_to_die.txt:64` 附近调用 `removeBuffsOnDie()`；当前 `effects.ts:293` 的伤害致死只发阵亡事件。`StatusDefinition` 没有通用 `keepOnDie` 表达，复活 `:334` 只移除控制状态。

影响：没有专属清理的标记、减益等可能跨死亡/复活残留，尸体也可能继续被相关 handler 读取。应先建立死亡清理策略，再保留明确需要跨死亡的状态，不能一刀切全部删除。

### B. 优先标定：生命换算与完整输入

**B1：所有输入的生命统一乘 2.42，证据不足以证明它是全局常数。**

`battle-hp.ts:55` 固定 `BATTLE_MAXHP_MULTIPLIER = 2.42`，输入适配器 `:25` 对每个单位应用。文件说明这个数字由荒骷髅一组面板和生命伤害反推，并明确还需要第二个单位/场景验证。

确认的是“当前确实全局使用经验乘数”，不是“2.42 已被证明错误”。但它会系统性影响生命伤害、护盾、治疗、复活、血线触发和战斗长度，应优先获取第二个实测锚点以及真实模式配置。

**B2：输入模型没有完整复现乱斗属性生成。**

`createBattleState` 接收已有面板、可选点数和一个四件套 ID；缺少直接按官方 `attr_luandou`、`equip_suit_luandou`、`attr_scale`、随机属性缩放生成最终面板的完整流程。若外部已经给出准确最终面板，部分缺项可以由输入补足；仅靠基础面板加点不能保证还原活动配置。

### C. 覆盖面和 AI 仍有明显缺口

**C1：66 个条目只有通用普攻。**

`generic-fallback.ts:18` 注册一个通用基本攻击与最低血线目标策略，AI/机制都标 unsupported。例如须佐之男、天照、孔雀明王、鲸汐千姬、禅心云外镜、伊邪那美、龙珏等。带这些式神仍能跑出胜率，不代表专属技能已经参与。

191 个 partial 式神通常已实现部分甚至较多技能；不能都当成“没做”，也不能都算“已对齐”。逐个缺口见本次覆盖清单。

**C2：官方加权 AI 框架没有实际规则数据。**

`weighted-policy.ts` 有评分与选招函数；`run-battle.ts:279` 会尝试调用，但本次 **623 个已注册技能中 aiRule 数量为 0**。因此这条路径不产生正式加权选招，随后使用状态选招或各式神手写 policy。

44 个 verified AI 是本地声明/回归口径，不能解释成“44 个已与官方权重序列一致”。手写条件策略可能对常见场景成立，但候选优先级、随机目标与特殊血线仍需官方 AI 数据或连续实战事件核验。

**C3：嘲讽/混乱的通用反击动作仍是固定倍率。**

`run-battle.ts:306` 之后的普通嘲讽/混乱分支直接算 `ratio: .125`，没有执行该式神真正的普攻定义，因此多段、附带控制/减益、普攻专属触发等可能丢失。另一种 `forced-random-ally` 分支已经调用真实普攻，两条路径不一致。

这里确认实现差异；应核实官方强制普攻的语义，再决定具体改法，不能把任意固定倍率当成所有式神的游戏普攻。

### D. 多护盾、御魂改率与高级免疫

**D1：多个盾按施加数组顺序消耗，没有游戏优先级。**

`doDamangeShieldOrCage.txt:53` 附近有排序；原始 buff 表有 28 行 `shieldPrority`。当前导入没有保留该字段，`effects.ts:906` 的 `consumeShieldStatuses` 直接 `statuses.map`。

影响：多个盾叠加时先破哪个盾不同，进一步改变破盾被动、暴抗移除、溢伤和不溢伤保护。实际排序 key 的细节还需完整核验，但当前没有优先级入口是确认缺口。

**D2：御魂概率缺通用可改写入口。**

游戏 `whenCalcYuHunRate` 构造结果并触发 `WhenGetYuHunRate`；引擎没有对应通用流程。以招财为例，`fortune-cat.ts:18` 直接用 0.5；御魂封印已有支持，但“改变御魂触发概率”和“御魂是否启用”是不同机制。

**D3：高级概率免疫/锁定等级未建模。**

游戏 `rateImmunityDebuff` 读取 `immunityProbability`、`skLock`、`ignImmunityLockValue`。引擎有确定性免控、抵抗、保护次数等规则，但缺上述通用组合和免疫结果账本；导入也未保留锁定字段。

**D4：加状态前的通用可改写钩子未闭合。**

`skillAddBuff` 有 `BeforeAddBuff` 与参数容器；当前多数路径先按命中/抵抗投骰，再应用和发 `status-added`。事后事件不能完整替代“上状态之前改概率/目标/参数”的语义。

### E. 还不能按官方种子精确复现

当前随机源是 `random.ts:14` 的 xorshift32；顶层还按阵容哈希/样本号派生种子。它保证本模拟器可重复，尚未实现或证明与游戏 Python `Random(seed)` 的序列兼容。

还有两个明确差异：

- 同速最终顺序：游戏排序使用 native UID，`action-scheduler.ts:33` 明确承认缺 UID，改用随机/阵营交替；甚至会增加随机数消耗。
- 控制命中区间：`control.ts:28` 明确保留低随机值成功的本地惯例，与客户端区间反向。同一原始概率分布可近似一致，同一 seed 的逐次成功/失败会不同。

所以取得官方 seed 后仍不能直接许诺复现同一串行动。还需随机算法、调用顺序、UID、AI、状态及事件顺序都一致。

### F. 其他待补范围

- **玄血**：没有独立 `xuanHp/normalHp` 模型。重伤由人工属性开关提供，`extHp` 是另一字段；已实现重伤算术不等于龙珏等玄血机制已实现。
- **模式规则**：输入没有完整 `battle_mode` 配置；目前统一使用部分 PvP 规则，不能从候选模式常量反推出实际竞猜模式。
- **终局**：默认 600 次行动后按剩余生命比例判胜，是模拟器兜底；没有证据证明这就是游戏竞猜超时判胜规则。触发预算超限也属于本地执行保护。
- **上限与次数**：参数级 `maxHurt` 有支持；官方 200 万全局兜底和每技能伤害次数统计并未因此自动接入。
- **范围判定**：AOE 打护盾实体有倍率模块，但 `core/context.ts:11` 仍按行动形态近似 `isRangeSkill`，缺官方范围集合/护盾实体完整识别。
- **时间与延期参数**：客户端时间锁、间隔、速度修改后的重排以及命中时延期求值，没有完整同构实现。个别内容的即时计算可能等价，不能据此宣布通用支持。
- **供火修正**：本次只有两个状态定义声明了 `resourceRecoveryBonus`。其余沉默/禁言行需要按具体 buff ID 匹配，不能按名称一律减火；推进时机和幅度仍需实测。
- **反汇编证据质量**：抓取目录的 `DISASM-JUMP-TARGETS.md` 明确记录前向跳转约 13% 未落在指令边界，且有未识别 opcode。因此早期交接中的“全部战斗函数真实逻辑已完整还原”不能照单全收，分支极性必须交叉验证。

## 建议推进顺序

1. **修通用生命周期**：施法者回合/整轮到期、死亡清理。先用完整 `runBattle` 交互验证，不能只测纯函数。
2. **核实生命与模式输入**：第二个生命换算锚点、模式配置，以及实际面板/点数/套装，避免系统性误差。
3. **补高频战斗交互**：真实强制普攻、多盾优先级、御魂概率改写与上状态前钩子。
4. **按真实候选池补内容**：先补活动常用的 unsupported 式神，再收口已有 partial 规则。
5. **增加技能等级真值与官方 AI 证据**：全 ID 覆盖不能替代逐级数据和自动策略核验。
6. **最后验证回放与概率**：同 seed 做逐行动首个分歧定位；有真实逐局输入后再做胜率校准。两种验证的目标和指标分开报告。
